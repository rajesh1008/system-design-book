fig-25-1: A loop drawn top to bottom: the harness assembles the context, the model proposes one step, the gateway runs or refuses it, and the observation goes to the trail and the next context. The harness then asks whether any stop condition is met; if not, the loop repeats, and if so, it stops with the reason.
fig-25-2: A boundary labeled the harness, servicing 1.0.0, which the customer or desk enters. Inside it, the loop sits beside the stop conditions and budgets that bound it, reads from the context policy, calls the model through the Gateway with the emphasized arrow, and acts through 14 tools. The Harness Manifest, hash 6b225e5fa425, is linked to the parts it names.
fig-25-3: A class diagram of the manifest, which holds a name, version, owner, loop shape, and hash, and owns four sections: tools, 14 of them, each with a name, version, and description; a context policy of 48,000 tokens with pinned fields; four stop conditions, each with an id and a check; and budgets of 24 steps and $1.00.
fig-25-4: A sequence in which the deploy check asks the registry whether the harness hash is registered, the registry answers yes, 1.0.0, the deploy check starts the harness, and the harness writes each step and the stop to the trail with the hash.
fig-25-5: A table of five loop shapes. The highlighted state machine fits known, fixed steps and needs legal transitions; plan and execute fits known, variable steps and needs a checked plan; ReAct fits open-ended work and needs a step budget; reflection fits where a verifier exists and needs a retry cap; bounded search fits high-value work with a verifier and needs a branch budget.
fig-25-6: A table of eight responsibilities with the owner marked. The model owns reading the customer, choosing the next step, and wording the reply. The harness owns what a step may see, which tools exist, when the case stops, whether an effect happened, and how much it may spend.
fig-25-7: Weekly stacked bars of harness changes from January 1 to May 31, 2026, 117 in all, of which 41, hatched, went through no release, against diamonds for 8 model changes in four weeks of April and May. Lakeshore figures are illustrative.
fig-25-8: Three bars of refund conversations handed off: 1.2% for the build as released, 3.9% for the same build with the May 28 settings, and 1.1% for harness 1.0.0 from June 8 to 30. Lakeshore figures are illustrative.
fig-25-9: A flow from a candidate harness manifest to a suite generated from it, covering stops, budgets, tool errors, context, and transitions. If all pass, the hash is registered; if not, the fix goes back to the manifest as a new version.
fig-25-10: A sequence from Wednesday night to Thursday afternoon. At 9:40 p.m. a settings file tells harness build 2026.05.26-1 to keep three turns; the 2:00 a.m. golden run passes 42 of 42; customers are asked for their booking again; the desk reports hand-offs at 3.9%; a diff at 1:30 p.m. finds the edit and it is rolled back at 1:52 p.m.
fig-25-11: The harness on one page: the manifest in the repository and its harness tests feed a signed registry, which the deploy check reads before starting the running harness, which calls the model through the Gateway, calls tools through the tool gateway, and writes a trail with the hash.
fig-25-12: A state machine for refunds that snakes through two columns: intake, a model state, to gather, to assess, a model state, to propose, to permit, to execute, to verify, to done. Permit may also go to declined. Any state but permit may hand off to a person, and any transition not drawn is refused.
