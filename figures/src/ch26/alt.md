fig-26-1: A top-to-bottom flow in which the agent loop proposes calls to the tool gateway, marked one path, which also takes input from the registry of reviewed tools and from the policy engine's permissions; an emphasized arrow marked checked leads to the nine tool servers, which hold the credentials to the systems of record; a dotted arrow from the gateway goes to the trail, one line per call.
fig-26-2: A class diagram with the tool in the middle listing name, description, and kind; above it, its input with typed identifiers and no free text; to the left, its result with summary first and a token cap; to the right, its error with field and fix; below, on a dashed line, its registry entry with owner, scopes, and hash.
fig-26-3: A sequence among the client, the gateway, and the server: the client discovers the server through the gateway with its token and receives capabilities; it lists tools and the gateway compares hashes with the registry and returns reviewed tools only; it calls a tool with arguments, the gateway checks scope, schema, and policy, forwards the call, and the server returns a capped result.
fig-26-4: A flow in which the Lakeshore client agent reads a partner's agent card listing skills and authentication, sends a task to the partner's remote agent, drawn with a dashed border as external, which returns a task with status and artifacts; an emphasized arrow marked a claim leads from the task to a check against Lakeshore's own records.
fig-26-5: A top-to-bottom chain of gates for a tool call carrying caller, server, and tool: authenticated; registered, approved, and hash matches; in the caller's grant with code mode for reads only; arguments valid; for effects, a permission for these arguments; within rate; then forward with output capped. A red arrow, standing for any failed check, leads to a refusal with reason, field, and fix, and dotted arrows from the forward step and the refusal lead to the trail.
fig-26-6: A top-to-bottom flow from a submission to a screen to a reviewer, Owen Fletcher, who either approves, along an emphasized arrow to an approved entry whose hash is kept, or rejects, along a red dashed arrow to rejected; the served text and the approved entry both feed a hash-match check, and a red dashed arrow marked changed leads from the check to rejected.
fig-26-7: A horizontal bar chart of tokens for one refund check with eleven calls either way: in the final context, direct calls use 2,491 and code mode 984; processed across all turns, direct calls use 27,467 and code mode 1,794.
fig-26-8: A flow in which the model, holding a search tool and three always-loaded tools, sends a query to a filter by the caller's grant, which draws on the registry of approved tools only; the results are ranked by name and description, the top three definitions load back to the model along a dashed arrow, and the model's call goes along an emphasized arrow to the gateway's call checks.
fig-26-9: A sequence among a person, an agent, the policy engine, and a merchant: the person gives the agent a mandate; the agent asks the policy engine whether the purchase may happen and receives a permission; the agent pays the merchant with the mandate, the merchant settles and returns a receipt; a red dashed arrow shows a payment over the mandate.
fig-26-10: A four-row scorecard with columns line, value, and owner: tools behind the gateway, 14, Daniel Price; calls logged from June 8 to 21, 100%, Ben Carter; rejected at registry review, 2, Owen Fletcher; tool errors the agent resolved, 77%, Hannah Clarke.
