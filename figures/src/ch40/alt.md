# ch40 alt text (one line per figure; copied into 03-figures/alt.md for the build)
fig-40-1: A table comparing Lakeshore's project control plane on August 10, 2026, with the platform on August 31, one row per question: callers written in code against callers issued from manifests; policy holding only servicing's rules against rules per use case; a run token bound to one trip against one bound to the use case's own resource; one golden set against one for each use case; and, in a highlighted last row, maturity read as a level against evidence-chain coverage of two of three use cases.
fig-40-2: A top-to-bottom diagram of what the platform centralizes: use cases keep their own prompts and models, shown beside them; every call passes identity, which mints run tokens, then the shared gateway, which forwards only tools the registry approved, then the policy engine, which sends allowed calls to the tool servers and writes to a store of trail, traces, and evaluation.
fig-40-3: A table of what Lakeshore leaves to teams, each with the platform's one line: prompts, with no limits inside them; retrieval, with sources named and cost charged; model choice, pinned and called through the gateway; tool servers, registered and reviewed; golden tasks, thirty or more, run by the platform; and the result, which needs an owner outside the team.
fig-40-4: A top-to-bottom flow of the paved road: a manifest written by the team passes the template check, gets an identity from the manifest, has only its new tools reviewed in the registry, goes to one review of tools, rules, and golden set, runs in staging as shadow runs, and passes six conformance tests to go live; any failed test loops back to the manifest.
fig-40-5: A horizontal bar chart of onboarding time from start to live: the desk assistant, onboarded by meeting from June 22 to July 23, 2026, took 31 days and 11 meetings in five stages; the loyalty assistant, on the paved road from August 17 to 26, took 9 days and one review in four stages.
fig-40-6: A line chart of monthly cost in thousands of dollars against the number of use cases from one to ten: one control plane per use case rises steeply from about 22 thousand to 225 thousand; the shared plane, dashed, rises gently from 57 thousand to 75 thousand; the lines cross at a marked break-even of 2.7 use cases, and Lakeshore's three use cases sit just past it.
fig-40-7: A sequence diagram of the bypassing use case: the loyalty agent sends ten calls to the shared gateway, which forwards ten to the points server; one call, in red, goes straight to the points server on the old ledger key; conformance reads a count of eleven from the server and ten from the trail, and test K2 fails, in red, back to the loyalty agent.
fig-40-8: A table of what this chapter covers and what the companion volume on platform engineering covers at depth: for the platform team, what it owns against team design; for the portal, one manifest against portals and catalogs; for golden paths, one for agents against many and their upkeep; for adoption, one onboarding against measuring it; and for funding, fixed plus marginal cost against budgets and showback.
