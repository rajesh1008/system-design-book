# ch29 alt text (one line per figure; copied into 03-figures/alt.md for the build)
fig-29-1: A top-to-bottom diagram: the agent loop either calls a named tool, which does one reviewed action through its schema, or starts a code run, which can do any action it can reach; the code run passes through a sandbox per run and its egress list before it reaches the systems and the host.
fig-29-2: A vertical stack of layers a code run passes through, outside in: a code run in a fresh directory, then filesystem (own directory only), network (proxy, listed hosts), secrets (none injected), and limits (cpu, memory, wall clock), ending in the environment discarded after the run; a dotted arrow from the network layer sends refusals to the trail.
fig-29-3: A five-row table with columns class, escape path, and control: filesystem, host files and symlinks, own directory only; network, the replica, metadata and DNS, proxy to listed hosts; secrets, environment, keys and transcripts, nothing injected; limits, spin, memory and fork, cpu, memory and wall caps; persistence, files left for the next run, fresh per run.
fig-29-4: Paired horizontal bars for five probe classes of eight probes each, the shared runner as found against the sandbox per run: filesystem 5 against 0, network 8 against 0, secrets 8 against 0, limits 8 against 0, persistence 8 against 0, for totals of 37 of 40 against 0 of 40.
fig-29-5: A top-to-bottom pipeline: a ticket tagged agent-ok goes to the coding agent, which proposes a branch; CI runs in a sandbox and reports on the head commit; the review gate checks tests, owners, and approval, with a code owner approving; only the merge service merges.
fig-29-6: A sequence diagram with the coding agent, the CI sandbox, the gate, and the test owner: the agent pushes a branch without the failing test, CI passes on five tests, the agent tells the gate CI is green, the gate sees six tests become five and holds, asking the owner for approval; the agent then fixes the cause, CI passes on six tests, and the owner approves the head.
fig-29-7: A top-to-bottom preference order for getting data from a supplier: first an API, at 0.4 seconds; next a reviewed tool; last a read-only browser reader, whose requests pass an egress list of portal hosts, with any submit or unlisted host refused.
fig-29-8: A four-row table with columns actor, may, and may not: code run may use its own directory and listed hosts, may not reach secrets, the host, or the next run; coding agent may push agent branches and open a proposal, may not merge, approve, or edit owners; browser reader may read listed portals, may not submit or reach other hosts; merge service may merge an approved head, may not merge on a stale approval.
fig-29-9: A five-row scorecard with columns line, value, and owner: escapes in the sandbox per run, 0 of 40, Owen Fletcher; agent pull requests June 22 to 28, 38, Daniel Price; held by the gate, 4, Tomás Ruiz; protected-test deletions merged, 0, Ben Carter; browser reader, staging, Hannah Clarke.
